# «Цифры команды»

Внутренний Telegram-бот в `lib/databot/`. Отчёты и управление задачами доступны в личке по приглашению. Только учёт закреплённых задач и команда импорта работают в настроенном командном чате. Остальные группы бот покидает. Это отдельный бот от `lib/team/` и бота участников.

## Запуск

Нужны миграции проекта, включая `037_databot.sql` и следующую за ней `038_databot_tasks.sql`, серверный доступ Supabase и переменные `DATABOT_TOKEN`, `DATABOT_WEBHOOK_SECRET`, `DATABOT_OWNER_IDS`, `NEXT_PUBLIC_APP_URL`. Владельцы задаются Telegram ID через запятую и входят через `/start`; дальнейшее управление доступом доступно из раздела «Команда».

Production webhook `/api/telegram/databot-webhook` регистрируется при старте приложения. Для разработки — `npm run databot:dev` с отдельным тестовым токеном в `.env.local`. Скрипт отказывается снимать обнаруженный production-webhook. Реальные токены не нужны для unit-тестов.

В репозитории нет настроенной команды применения миграций. Администратор сначала проверяет, что `037_databot.sql` применена, затем выполняет полный файл `supabase/migrations/038_databot_tasks.sql` через Supabase SQL Editor и проверяет появление таблиц `databot_tasks`, `databot_task_claims` и функций `databot_task_*`. После этого задаёт переменные чата и топиков в окружении сервера и перезапускает приложение, чтобы вебхук получил `edited_message` в `allowed_updates`.

## Подключённые разделы

| Команда | Раздел | Доступ |
| --- | --- | --- |
| `/runs` | Забеги, участники, план явки и динамика | По матрице доступа; персональные списки доступны Совету и Ивентам в ограниченном окне |
| `/kb` | Справочник | Статьи своей зоны; Совет читает все и редактирует |
| `/team` | Команда и использование бота | Совет; управление участниками — владелец |
| `/pro` | Про и оплаты | Совет |
| `/product` | Продукт | Совет |
| `/tasks` | Мои задачи, общий пул и свободные слоты | Каждый действующий участник |

## Задачи команды

Задайте `DATABOT_TASK_CHAT_ID` (отрицательный ID командной супергруппы с топиками) и `DATABOT_TASK_SOURCE_THREAD_IDS` (ID топиков источника через запятую). По умолчанию бот публикует взятую задачу в тот же `message_thread_id`, что и исходное сообщение. Если нужен один отдельный рабочий топик для всех источников, задайте `DATABOT_TASK_WORK_THREAD_ID`; это явное соответствие всех исходных топиков одному рабочему. Значения не подставляются из примеров. Пока ID чата и исходных топиков не заданы, группа не становится разрешённой.

Администратор получает ID из апдейта `message.chat.id` и `message.message_thread_id`. В разработке `npm run databot:dev` печатает оба ID; после настройки чата владелец может написать `/task_ids` в нужном топике. Личный `/task_ids` показывает собственный Telegram ID. У бота должны быть права администратора на отправку сообщений и закрепление в командной группе. `allowed_updates` включает `message`, `edited_message`, `callback_query`, `my_chat_member`. Чтобы бот получил исходные сообщения и событие закрепления, отключите privacy mode у него в BotFather и проверьте поступление апдейтов. [Telegram Bot API](https://core.telegram.org/bots/api#message) передаёт `pinned_message` как служебное сообщение, а `message_thread_id` указывает топик.

Задача — одно отдельное сообщение. Используйте строгие строки (срок с явным часовым поясом, пример московского времени):

```text
Что: подготовить и опубликовать страницу
Кто делает: @username
К какому дню и часу: 2026-10-01T18:00+03:00
Ссылка на результат: да
```

Последняя строка необязательна: без неё ссылка на результат не требуется. Дополнительные строки описания сохраняются в поле «Что». Простая реплика задачей не считается. Закрепите исходное сообщение или дайте владельцу ответить на ранее опубликованное сообщение командой `/task_import`. Если ранее опубликованное сообщение уже закреплено, после импорта закрепите его повторно: только увиденное событие закрепления позволяет боту безопасно снять именно этот закреп при завершении. Повторное закрепление и импорт сохраняют тот же `(chat_id, message_id)`; правка доступной задачи обновляет её по `edit_date`. Неполная правка исключает задачу из пула, пока сообщение не исправлено. После взятия исходный снимок задачи не меняется.

Перед выбором владелец подтверждает исполнителя в личке: `/task_bind ID_задачи Telegram_ID`. Бот сравнивает ник точно без `@` и с приведением регистра, сверяет живой профиль через Telegram и список действующих участников. При отсутствии ника, неоднозначности или его смене участник обновляет профиль через `/start`; владелец, проверив Telegram ID человека, использует явное исправление `/task_rebind ID_задачи Telegram_ID`. Бот никогда не передаёт задачу другому ID из-за смены ника.

В личном разделе «Мои задачи» видны задачи подтверждённого исполнителя, активные задачи и свободные слоты. Кнопка «Взять задачу» атомарно проверяет членство, привязку, статус и лимит. Сначала можно взять до четырёх задач; затем новую можно взять после завершения одной из ранее взятых, когда освободится слот. Одновременно активных задач не больше четырёх. После выбора бот публикует отдельное HTML-сообщение в рабочем топике и закрепляет его. Если Telegram не подтвердил публикацию или закрепление, бот сообщает о незавершённом шаге: запись о взятии уже сделана, повторное нажатие не создаст вторую публикацию. `/mytasks` и `/task_retry ID` показывают и повторяют закрепление. Явный отказ Telegram 4xx можно повторить через `/task_retry ID` после исправления прав. При неопределённом сетевом результате новый `sendMessage` автоматически не вызывается: владелец проверяет рабочий топик и отвечает `/task_recover ID` на обнаруженное сообщение бота. Если сообщения нет, администратору нужно разобраться с записью `sending/uncertain` вручную до повторной отправки: Telegram не предоставляет ключ идемпотентности для `sendMessage`. Сохранённые состояния отправки нужны потому, что вебхук отмечает апдейт обработанным до вызова бота и возвращает HTTP 200 даже при ошибке.

Если при `sending/uncertain` опубликованного сообщения нет, владелец после проверки рабочего топика и ожидания не менее минуты отправляет в личке `/task_reset_send ID no_message`; затем исполнитель повторяет `/task_retry ID`. Проверка отсутствия обязательна: Telegram не предоставляет ключ идемпотентности для `sendMessage`.

Кнопка «Завершить» доступна самому исполнителю. Если задача требует ссылку, бот просит отправить `/task_done ID https://…` и сохраняет её в записи задачи. Сначала задача переходит в `completing`: слот остаётся занятым. Бот снимает закрепление конкретного опубликованного сообщения и, если задача попала в пул по закреплению, конкретного исходного сообщения. Затем бот редактирует **своё** сообщение с зачёркнутым текстом; сообщение автора остаётся без правки. Лишь после подтверждения всех шагов статус становится `done` и освобождается слот. При сбое действия повторяются через кнопку «Повторить оформление» в «Моих задачах» или `/task_done ID`. Общий `databot_audit` хранит только вид операции и код ошибки — тексты задач и ссылки результата туда не записываются.

`/social` пока отвечает, что раздел ещё собирается. Текстовые вопросы сейчас ищут статьи справочника; произвольный запрос к отчётам через LLM не подключён.

## Про и оплаты, Продукт

По умолчанию показывается текущий месяц. Кнопки переключают период: **7 дней**, **прошлая неделя**, **этот месяц**, **30 дней**. Границы считаются по Москве; текущие периоды заканчиваются в момент запроса. Прошлая неделя — законченные понедельник–воскресенье. Длинные списки разбиты на страницы с кнопкой «Ещё»; при каждом запросе данные читаются заново.

Оба раздела используют существующие RPC `databot_pro` и `databot_product` из миграции `037`; новых таблиц и миграций для экранов не требуется. Ошибка БД отображается как ошибка, а не как нулевой отчёт. Смена периода записывается в аудит. Права проверяются и для команд, и для нажатий кнопок; СММ и Ивенты не получают эти данные.

### `/pro`

- Количество PRO сейчас с разделением на оплату, промо и ручную выдачу.
- Количество и сумма успешных оплат за период, разбивка по планам.
- Погашения промокодов за период и разбивка по кодам.
- Сколько пользователей, погасивших промо в периоде, оплатили позже — по всем имеющимся последующим оплатам, не только внутри выбранного периода.
- Количество пользователей PRO с активной подпиской, истекающей в ближайшие 7 дней.

PRO сейчас и ближайшее истечение подписок — текущий снимок, они не меняются при выборе исторического периода. Суммы — в рублях, копейки сохраняются. Аккаунты команды исключает SQL.

### `/product`

- Регистрации за период; из этих пользователей — прошедшие онбординг и имеющие активную привязку Telegram по текущему состоянию.
- Активные пользователи за 7 дней до конца периода — все пользователи, а не только новые регистрации.
- Спринты, начатые и закрытые за период; отдельно — активные сейчас.
- Отправленные утренние сообщения и переходы по ним.
- Регистрации по каналу последнего касания.
- Возврат после пропуска: пока **«нет данных»**, потому что RPC возвращает `nsm=null`.

Текущая SQL-функция считает утренние сообщения по полным московским календарным дням: сегодняшний неполный день не входит. Экран прямо подписывает это ограничение. Аккаунты команды исключены из расчётов.

## Код и проверки

- `sections/summaries.ts` — обработчики двух отчётов, подписи метрик и страницы.
- `data/pro.ts`, `data/product.ts` — чтение и валидация RPC.
- `intent.ts` — разбор команд и кнопок периода/страницы.
- `access.ts` — единая матрица доступа.
- `sections.ts`, `handlers.ts` — включение разделов и регистрация обработчиков.

```sh
npm test -- lib/databot/sections/summaries.test.ts lib/databot/pipeline.test.ts lib/databot/access.test.ts lib/databot/privacy.test.ts
```

Тесты проверяют московские границы периода, права до чтения данных, ошибку БД, аудит, экранирование HTML, различие нуля и отсутствия данных, сохранность длинных списков и лимиты Telegram.
