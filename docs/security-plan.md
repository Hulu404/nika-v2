## P0 — Защита от финансового/ресурсного abuse

Главный риск проекта: открытая регистрация + отключённые лимиты + отсутствие rate limiting = любой может бесплатно и бесконечно жечь бюджет Anthropic API и часы Railway.

1. **Вернуть лимиты.** `lib/subscription.ts` → `FORCE_PRO_FOR_ALL = false`. Если флаг нужен временно для тестов — завести отдельный механизм (allowlist по user_id), а не глобальный выключатель.
2. **Rate limiting на `/api/chat`.** Лимит по `user.id` (например, через Upstash Redis с `@upstash/ratelimit`, благо Railway хорошо дружит с внешним Redis) — N запросов в минуту/час сверх дневного лимита `FREE_DAILY_LIMIT`. Возвращать 429 с понятным сообщением.
3. **Rate limiting на `/api/auth/register`.** Лимит по IP (например, 5 регистраций/час с одного IP) + капча (Cloudflare Turnstile — бесплатный, легко встраивается в Next.js) перед вызовом `admin.createUser`.
4. **Лимит для Telegram-бота.** В `bot/src/bot.ts` добавить per-user rate limit (простая in-memory карта `userId → timestamps` или `grammy` middleware `@grammyjs/ratelimiter`), иначе бот — второй открытый канал для того же abuse.
5. **Алерты по тратам.** Включить budget-алерты в Anthropic Console (уведомление при превышении дневного/месячного порога) — это backstop, если лимиты в коде где-то не сработают.

## P1 — Аутентификация и API-эндпоинты

6. **Убрать раскрытие деталей ошибок** в `/api/auth/register`: не возвращать `error.message` от Supabase клиенту напрямую (позволяет user enumeration — узнать, какие e-mail уже зарегистрированы). Замаппить на generic-сообщение, детали — только в `console.error`.
7. **Политика паролей** при регистрации (минимальная длина, проверка на топ-1000 паролей) — Supabase это умеет на уровне проекта (Auth → Policies), включить там же.
8. ✅ **`SameSite` cookie — проверено, действий не требуется.** `@supabase/ssr` ставит `sameSite: "lax"` по умолчанию (`DEFAULT_COOKIE_OPTIONS`), в коде не переопределяется. Cross-site POST не приложит cookie → CSRF на `/api/chat` неактуален. ⚠️ Тот же дефолт содержит `httpOnly: false` — cookie сессии читается из JS (требование браузерного SDK Supabase, не меняется без смены подхода). Последствие: XSS = кража сессии, поэтому защита от XSS критична (см. security-заголовки ниже + CSP в backlog).
9. ✅ **CORS — проверено, действий не требуется.** На API-роутах CORS-заголовки не выставляются, permissive `Access-Control-Allow-Origin: *` нигде нет → браузер блокирует кросс-оригинные чтения по умолчанию.
9a. ✅ **Security-заголовки добавлены** (`next.config.mjs`, на всех маршрутах): `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/mic/geo off), `Strict-Transport-Security`. Проверено вживую на `/auth`.
9b. 🟡 **CSP — фаза Report-Only (наблюдение).** Nonce-based CSP в `middleware.ts` (per-request nonce, `Content-Security-Policy-Report-Only`), nonce проставлен инлайн-скриптам в `layout.tsx`. Проверено: nonce заголовка совпадает со скриптами, все `<script>` на app-страницах помечены. `script-src` с `'strict-dynamic'`, `style-src 'unsafe-inline'` (inline style-атрибуты), Yandex.Metrika в img/connect-src. **Перед переключением на enforcing нужно:** (1) собрать реальные нарушения в браузере (DevTools → Console) на всех экранах + Yandex webvisor; (2) решить судьбу `landing.html` — статический файл с 6 инлайн-скриптами без nonce (под enforcing заблокируются): нужны хеши/отдельная CSP для лендинга/перенос в React; (3) покрытие вне matcher'а middleware (`/upgrade`, `/manifesto`) CSP не получает — добавить при enforcing.

## P3 — Процессы и мониторинг

14. **Секрет-сканирование репозитория.** Подключить GitHub secret scanning (для публичного репо `Hulu404/nika-v2` он уже частично включён GitHub-ом по умолчанию, но стоит добавить pre-commit hook, например `gitleaks`, чтобы ловить секреты до пуша, а не после).

16. **Ротация секретов по графику.** Завести правило: ключи (`ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `BOT_TOKEN`) меняются раз в N месяцев или сразу после любой возможной утечки (например, после показа в чате/скриншоте/логе).
17. **Healthcheck и алерты Railway.** Настроить уведомления Railway о превышении лимитов плана (CPU/память/часы), чтобы узнать о DoS-атаке раньше, чем приложение просто упадёт.
18. **RLS — держать в порядке.** Текущие политики в `002_rls.sql` корректны; при добавлении новых таблиц — сразу писать RLS-политику в той же миграции, не откладывать на потом.
